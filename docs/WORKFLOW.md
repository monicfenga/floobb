# WORKFLOW — 批次执行流程（两回合制）

> 基于 Phase 0（地基）实际执行经验固化。适用于 Phase 1 各批次及 Phase 2 SNS。
> 启动一个批次只需说：**「按 WORKFLOW.md 启动批次 N，任务是 XXX」**。

## 0. 启动时 AI 必读（按序）

1. `docs/SPEC.md` — 唯一事实来源。**§9 已决议的 11 条不要重新提问、不要翻案**。
2. `docs/kickoff.md`（或对应批次的开工指令）— 本批次的任务边界。
3. `.workbuddy/memory/` 当日及近期日志 — 决议与上下文（append-only，只读不写历史）。

## 1. 第一回合：只读盘点（不修改任何文件）

读完必读材料后，产出以下清单交用户确认，**回合结束即停**：

1. **现状/兼容扫描清单**：逐条列出「文件路径 + 行号 + 命中项」。扫描范围按批次任务定（Phase 0 用的是 PHP 8 兼容清单，见 kickoff.md）。
2. **组件/方案映射表**：吸纳/复用什么源文件 → 落到哪里 → 逐条列明适配点。（无吸纳任务的批次可省略或改为「实现方案要点」。）
3. **文件影响面清单**：本批次各项任务分别 新增/修改/删除 哪些文件。涉及搬迁函数/类时，**必须先 grep 全项目引用点并一一列出**。
4. **待确认问题区**：清单末尾放「待定项」，由用户判断，AI 不擅自决定。

**等用户回复"确认"后才进入第二回合。** 用户可能会逐条改清单，以改后的为准。

## 2. 第二回合：执行 + 验收

- **只做清单内的事**：不顺手扩改、不重命名、不调无关代码风格。需要额外改动才能完成时，**先列方案等确认，不要直接改**。
- 写操作只限 `M:\laragon\www\floobb\` 内；参考项目一律只读。
- **破坏性操作（删文件、删原定义、reset/checkout、合并等）先确认再执行**；删除函数定义前 grep 核对无遗漏调用点。
- 完成后逐项验收并 **checkbox 汇报**：
  - 每个改动文件跑 `php -l` 语法检查；
  - 用 `curl` 打 `http://127.0.0.1/floobb/` 相关路由验证真实可用（Laragon Apache :80 已在跑；**禁止自起临时服务器**）；
  - 汇报格式：改了哪些文件 → 验证结果 → 遗留问题。

## 3. 收尾

- 把进展追加到 `.workbuddy/memory/` 当日日志（append-only）：做了什么、验证结果、遗留问题。
- **每块验收通过后必须同步更新 `docs/ROADMAP.md`**（人看的进度表，十行以内）：该块状态行改为「✅ 已验收」/「🔄 推进中」+ 一句要点；已定死的决策、剩余待办也记在该文件对应区块下。这是每次收尾的固定动作，不是可选。（文件名曾为 PROGRESS.md，2026-10-30 起改为 ROADMAP.md）
- 提交只在用户明确要求时做；**不主动 push、不建远程**。
- 不抢下一阶段的活（边界由批次任务划定）。

## 4. 沟通与硬约束（每回合都适用）

- **发指令规则**：架构级改动与功能改动分开发指令，**一条消息一个可验收的改动**。架构级改动（namespace、ID 策略、目录结构、数据层方案）单独一条指令、独立验收后再开下一条；功能改动（新字段、新控制器、新模板）单独一条。一条消息混装两件互不相干的改动 = 回归互相污染排查面，无法二分定位
  - （2026-10-30 实证：去 namespace 与版块 slug 同回合下发，Auth.lib 残留引用报错时多烧一轮）。AI 接到混装指令时主动提醒拆分后再动手；每条指令结束时站点应处于可刷新、可验收、可回滚的状态。
- 结论先行；有歧义先问，不猜。
- 硬约束沿袭 SPEC §1：PHP 8.4、无构建步骤、Flatdb JSON 唯一数据层、关联数组 + 静态仓储函数、三位置契约路由、不服务器发邮件、模板站内链接一律 `Router::url()`。
- 常量在 `init.php` 已定义的直接引用，不重定义。
